## 2026-08-18 (3) — IndexLogger rotated every index by one; kf_domain retired for one in-memory pose function
- **Goal:** validate the single pose function (Paul: "caches and jsons are the
  wrong path") before tombstoning kf_domain. The acceptance gate — new function
  must reproduce the old kf_domain cache — FAILED with K+2 on 05 and 02, and
  the investigation found a C++ bug older than every lift we have run.
- **The bug (index_log.h):** CreateIndexFile stored ReadNextBytes() AFTER each
  read — the start of record k+1 — as entry k. Every .index was rotated by one
  (entry 0 -> record 1, record 0 reachable only through trailing garbage), the
  failed reads at EOF appended phantom ts=0 entries, and OpenIndex pushed its
  own failed final read (offset 0 -> record 0 duplicated at the end). Measured
  on 05: C++ saw N+2 entries, head=record 1, tail=[0, 0, record 0]. This is
  ten_rows' 1790-vs-1792 AND its 18.3 s ts[0] mystery in one bug.
- **Blast radius:** LaserProjector reads images through the same IndexLogger,
  so every lift to date (cluster_tree_instances, markers_v2_from_sam3, all
  surveys) paired frame K's masks with frame K+1's image/pose/laser — a
  systematic ~0.2 m along-track smear in every lifted marker. The morning's
  SAM3+scene_graph quarantine therefore also flushes mispaired geometry.
- **Fix:** offsets captured BEFORE the read; entries written only when the
  stream advanced; OpenIndex checks EOF after reading, before pushing
  (aru_sil_core 313bb9a3). Index rebuilds on every open, so no stale sidecars
  survive. Verified on 05: file-order wire parse == C++ index == legacy python
  reader, n=3386, strictly increasing (K IS incremental, as it must be for a
  20 cm cut of a time-ordered stream — Paul's invariant).
- **kf_domain retired (973628ff):** survey_paths.poses_at_keyframes() reads the
  two monolithics in memory — timestamps via the fixed C++ reader, increments
  wire-parsed, slerp at kf timestamps, L2C conjugation. Bitwise-identical to
  the retired cache on 05 and 02 (max|dT|=0.0). kf_pose_records/kf_pose_dict
  keep the old shapes; 12 consumers swapped; kf_domain.py/kf_poses.py raise
  with the successor named. ONE pose json per block (transforms.json, refine
  rewrites it in place with refined_per_pass:true); kf PNGs are regenerable
  renders in prod/scratch_sam3, count-gated against the mono; pipeline [4]
  quarantines any transforms.json whose first frame path is dead (all 439

## 2026-08-18 — ten_rows: two silent faults (1-byte index, camera-frame poses); laser lift fixed, clustering still citrus-tuned
- **Goal:** why `cluster_tree_instances` reported "0 world points" on
  dec_2025_ten_rows for seven consecutive queue slots.
- **Data:** /home/paperspace/data/klapmuts/dec_2025_ten_rows (1790 kf, 3943

**Fault 1 — a missing file became a 1-byte index.** No single directory
resolved all three monolithics the LaserProjector needs: the survey root had
`transform_lio` + kf mono but no `laser.monolithic`; `monolithics/` had laser +
kf but no `transform_lio`. The pipeline passes the root, so IndexLogger was
pointed at a non-existent laser mono and CREATED a 1-byte index for it

specified position!". Every `project()` then returned empty. Rebuilt beside its
mono the same index is 27,433 B (04's is 52,969 B). **A missing input is
indistinguishable from an empty one in every C++ reader we have.**

**Fault 2 — camera-frame poses fed to a lidar-frame contract (Paul's call).**
readiness R1 aliases `transform_lio -> monolithics/zed_transform`, which is ZED
= CAMERA frame, while `c2w = L2C*Tf*L2C^-1` assumes LIDAR frame. Conjugating an
already-camera-frame pose does not cancel, so every frame picks up its own
spurious rotation. Single-frame reprojection CANNOT see this (the pixel path is
`L2C*T_motion*p_lidar`, Tf never enters) — it took accumulating six neighbour
scans into one anchor frame: at kf 900 they came back as VERTICAL streaks
(figs/tenrows_worldcloud_kf0900.png), and at kf 0 only 4,678 of 75,459 points
stayed in frustum.

- **Fix:** `T_lidar = L2C^-1 * T_cam * L2C` per relative increment; conjugation
  telescopes, so prod's c2w collapses to exactly Tf_cam and NO downstream code
  needs a ten-rows branch. New `ensure_laser_frame_poses.py` (detects frame by
  flat trajectory axis, converts, aliases both dirs, unlinks sub-64-B indexes),
  wired into readiness as R1b.
- **Result:** c2w(new) == Tf_cam(old) to 1.3e-6 at kf 0 / 1.27e-4 at kf 1500 —
  float32 storage in pbMatrix, relative error 1.6e-6 ≈ 13x float32 eps, NOT a
  frame error (it grows with accumulated distance). World cloud through prod's
  unmodified path reproduces the H2 panel exactly: 75,459 pts at kf 0, 16,313 at
  kf 900. Clusterer: 0 -> **16,989 world points**, voxel grid 52.3 x 4.5 x 61.5 m
  (a physically sane tunnel). Frame check across the fleet: ten_rows flat=y
  (camera, converted); apr_2026_zed, 01, 02, 03, 04, 05 all flat=z (laser, left
  alone) — a blanket conversion would have corrupted five healthy surveys,
  apr_2026_zed included despite its name.

## 2026-08-22 — stage1 was spending 87% of its time decoding zeros: one gate, 7.5x faster
- **Goal:** Paul's question — stage1 trains with features off, so it is "basically splatfacto";
  would running splatfacto and initing HiGH from it save time? A/B at 2k iters.
- **First result (2k iters, quarter-res under num_downscales=2):** `ns-train high` 34.2 ms/iter
  vs `ns-train splatfacto` 20.8. Ablations priced the optional losses at only 2.8 ms total
  (tree-LOD 2.8, sky 1.5, masked metrics 0.7) — so ~13 ms was structural, NOT recoverable by
  switching off losses, and switching to splatfacto would have cost tree-LOD (+1.2 dB TREE,
  -15% gaussians) for the smaller half of the saving.
- **Chasing the ~13 ms — nine falsified hypotheses:** datamanager (7.5 vs 7.9 ms), get_loss_dict
  (1.6 vs 1.4), the 32-D feature machinery and the second rasterisation pass (both correctly
  gated), gsplat kwargs (identical), the rasterisation itself (6.05 vs 6.55 ms under explicit
  torch.cuda.synchronize), the uncompiled _get_viewmat (swapping in splatfacto's compiled one:
  35.2 vs 34.2 ms), the per-step [1,H,W,32] zeros allocation (caching it: 33.6 vs 34.2).
  **Every Python-level profiler mis-attributed the cost** because CUDA is async: un-blocked, the
  wait landed on get_metrics_dict (16.9 vs 5.4 ms — it calls torchmetrics PSNR, the first sync);
  under CUDA_LAUNCH_BLOCKING it moved to get_outputs (29.5 vs 15.3). Both were artifacts.
- **What found it:** a CUDA kernel trace (`--logging.profiler pytorch`). high ran
  `ampere_sgemm_128x64_tn` 11.58 ms + `GeluCUDAKernel` 1.28 ms that splatfacto never launches,
  while gsplat's fwd/bwd kernels matched to two decimals (5.55/11.69 vs 5.54/11.68). Op counts:
  5x aten::linear + 5x aten::addmm per step in high, ZERO in splatfacto. A forward hook on all
  82 nn.Linear modules then named it: `image_encoder.high_model.decoder.{0,2,4,6,8}`, input
  (230400, 32), via high_model.py:462 -> get_relevancy_from_high -> clip_encoder.get_relevancy
  -> hyperbolic_ae.decode_features.
- **Root cause:** the relevancy pass is guarded only by `len(self.image_encoder.positives) > 0`.
  The encoder config ships DEFAULT positives, so it is always true — stage1 decoded a ZEROS
  feature image through the 5-layer HyperEmbedder decoder for every pixel, every step, and threw
  the result away (stage1 never reads outputs["relevancy"]). The comment above the guard already
  said "During training with empty positives, skip the CLIP-similarity pass" — unreachable.
- **Fix + result (`high` bd101c4):** add `self.config.enable_high_features and` to the guard.
  Full length, 05_13D_Jackal lio_row100/block_000, identical flags:
  **50.9 min -> 6.8 min (4.9 -> 37.0 steps/s)**; train FG 22.97 -> 23.07, eval FG 18.57 -> 17.82
  (sd ~1.5), gauss 776,972 -> 795,902 (+2.4%, inside the +/-10% band). Quality unchanged.

  (num_downscales=2), and the decode cost is PER PIXEL — 230,400 vs 921,600.
